# ZE-137: Cypher mutation-lowering readiness

Audited source: `1209c45bbf5f61905c616a97113b00c54b3b62e8` (2026-09-19). This is a source-readiness result. No mutation runtime, side effect, TCK scenario, commit, recovery, or public API was executed.

ZE-137 is this research audit only. Coordination at completion assigns ZE-138 its current core-plan/search representation, binding/search seam, and `lowering/mod.rs` work. After ZE-138's compiled commit is complete, root can hand the shared lowering files sequentially to a new flat follow-up implementation ticket. That owner should extend the existing builder rather than create a second one; ZE-138 is not required to prebuild mutation arenas, finalization, or extension hooks. The intervening ZE-136 integration at `a3ecc9483723967f5a70fbbf47909b57d3399018` is documentation-only and does not change this audited product source.

## Verdict

**Yes. A substantive, production compiler component can proceed before the ZE-52/ZE-57 coordinator and execution integration.** Its boundary is one-shot scoped lowering of a complete mutating `BoundQuery` into a validated immutable `GraphPlan`, with no store admission, overlay construction, staging, result materialization, or publication.

The input is real rather than proposed: `BoundQuery` exposes the final AST, source-indexed typed expressions/facts, parameters, projections, output columns, and the dynamic deleted-entity requirement ([binding.rs:43-93](../../../crates/zeppelin-embed-cypher/src/binding.rs#L43-L93)). The core plan is also real: `Eager` and ordered `Mutate` operators already exist ([plan/mod.rs:261-286](../../../crates/zeppelin-embed/src/property_graph/query/plan/mod.rs#L261-L286)); `Mutation` already represents node/relationship creation, remove/set property, add/remove label, DELETE/DETACH, and progressive property RHS evaluation ([plan/mod.rs:455-508](../../../crates/zeppelin-embed/src/property_graph/query/plan/mod.rs#L455-L508)). Validation requires an immediate eager input, validates mutation items in listed order, adds newly created slots for later same-clause endpoints, and rejects graph reads after a write ([plan/validate.rs:238-283](../../../crates/zeppelin-embed/src/property_graph/query/plan/validate.rs#L238-L283), [plan/mutation.rs:4-101](../../../crates/zeppelin-embed/src/property_graph/query/plan/mutation.rs#L4-L101)).

This is plan construction only. The runtime source contains no physical implementation of `OperatorKind::Eager` or `OperatorKind::Mutate`; outside the validator those variants are not consumed. Staging is real but is a separate producer: `GraphBatchReadView` stages ordered create/replace/delete and progressive property/text reads ([staging/overlay.rs:44-207](../../../crates/zeppelin-embed/src/property_graph/staging/overlay.rs#L44-L207)), while its `StagedBatch` explicitly has no publication authority ([staging.rs:356-380](../../../crates/zeppelin-embed/src/property_graph/staging.rs#L356-L380)). `WriteMemory` is a distinct writer admission owner ([staging/memory.rs:5-24](../../../crates/zeppelin-embed/src/property_graph/staging/memory.rs#L5-L24)). Connecting those seams without the real writer/base-view coordinator would therefore be the prohibited fake integration.

## Smallest coherent component

After ZE-138 completes its compiled work and root transfers shared-file ownership, the follow-up implementation should add a private `lowering/mutation.rs` component and expose only a mutation-specific one-shot front door beside `compile_read_in`. The current read entry deliberately rejects every clause other than MATCH and projection, so this is an explicit compiler route rather than a hidden fallback ([lowering/mod.rs:106-127](../../../crates/zeppelin-embed-cypher/src/lowering/mod.rs#L106-L127)). The recommended entry is:

```rust
pub fn compile_mutation_in<'v, T, C: ReadContext<'v>>(
    source: &str,
    parameters: &[ParameterBinding<'_>],
    limits: CompileLimits,
    memory: &QueryMemory<'_>,
    context: &mut C,
    consume: impl for<'plan, 'facts> FnOnce(
        LoweredMutation<'plan, 'facts>,
        &mut C,
    ) -> Result<T, ParseError>,
) -> Result<T, ParseError>;
```

`LoweredMutation` should expose the validated plan, columns, copied source, expression/operator spans, parameters, retained owners, item-level mutation spans, and `requires_deleted_runtime_validation`. That field carries the compiler's additional alias/deletion obligation to ZE-52 when true. A false value carries no additional compiler-identified obligation; it is never a live-entity certificate and never permits the physical provider to skip deleted-entity checks. Keep the HRTB callback: it prevents plan/fact/backing escape and creates no public prepared handle. Reuse the existing sealed context and exact `QueryMemory` identity check ([lowering/context.rs:11-43](../../../crates/zeppelin-embed-cypher/src/lowering/context.rs#L11-L43)). Allocate every new arena through the same actual `QueryMemory`; `QueryArena` reserves real capacity before allocation ([query/resources.rs:49-72](../../../crates/zeppelin-embed/src/property_graph/query/resources.rs#L49-L72), [query/resources.rs:203-225](../../../crates/zeppelin-embed/src/property_graph/query/resources.rs#L203-L225)).

The minimal new representation is compiler-owned:

- `DraftMutation` plus source-ordered draft/final mutation arenas; a shared symbolic-name arena/ranges supplies labels, relationship types, and property names.
- `DraftOp::Eager` and `DraftOp::Mutate(range)`, finalized to the existing core variants.
- An item-span arena parallel to finalized mutation items. Operator spans alone identify only the clause and a remapped slot expression can retain an earlier binding span.
- The dynamic deleted-validation bit copied from `BoundQuery`.
- Correspondingly larger `PlanBacking` region and `RetainedAllocation` inventories. The current read lowerer fixes 31 retained regions plus its fact owner ([lowering/mod.rs:535-622](../../../crates/zeppelin-embed-cypher/src/lowering/mod.rs#L535-L622)); new borrowed mutation/name/span arenas must be explicitly added, not hidden behind slice lengths.

No new core `Mutation`, coordinator adapter, public prepared-query API, parser, interpreter, dependency, or staging facade is needed. The follow-up implementation's primary new production path should be `crates/zeppelin-embed-cypher/src/lowering/mutation.rs`, with focused `crates/zeppelin-embed-cypher/tests/mutation_lowering.rs` coverage. ZE-138 need only finish its current compiled search/lowering scope. Root should then transfer ownership of `lowering/mod.rs`, `lowering/owned.rs`, and `lib.rs` to the mutation owner for any required arena, finalization, registration, export, or owner-inventory changes. This sequential handoff prevents concurrent edits while allowing the follow-up to extend the existing builder directly.

Component acceptance is limited to exact generated plan data and ownership: CREATE descriptors/slots/names/dependencies/property order; SET/REMOVE/DELETE/DETACH order; one eager barrier per update clause; Property-versus-Slot RHS structure; preserved explicit input order; optional/no RETURN; downstream LIMIT 0; static rejection plus dynamic deleted flag; source/item spans; exact parameter copying; real `GraphPlan` validation/fact ownership; allocation/control failure and nonescaping lifetime proof. A focused generated-plan case for `CREATE (a)-[r:R]->(b {x:type(r)})` must prove both node slots precede `CreateRelationship(r)`, and that `SetProperty(b, x, ...)` follows `r` with a `RelType` expression over its slot. A plan comparator should inspect descriptors, expressions, slots, barriers, spans, columns, and owners. It must not claim a mutation occurred or prescribe runtime ID allocation order.

## Mandatory gates that remain

ZE-52/ZE-57 still own every runtime and public acceptance gate: real writer admission and admitted base view; physical eager draining and frozen row/scalar backing; progressive `GraphBatchReadView` evaluation; actual property-list conversion; CREATE IDs and same-clause endpoints; revision/fence/NoOp behavior; ordered, tied, and unordered repeated-target joint outcomes; DELETE incident failure and DETACH neighbor preservation; post-delete output checks; late result/memory/type/cancellation rejection with no partial changes; precommit native/ABI result ownership; all side effects under LIMIT 0; definite versus indeterminate commit; no automatic retry; durable publication; close/drain; and public reopen state. The retained original mutation TCK inventory is `Create1[1-12]`, `Set2[1-3]`, `Set3[1-8]`, `Delete1[1-7]`, `Remove1[1,3,5,6]`, `Remove2[1-5]`, and `Remove3[1,15]`. Local acceptance separately retains list-index, multiple-item, and missing-property REMOVE; EmptyList and homogeneous-list failures; mixed structured revision edits; unsupported deleted graph-value/property outputs; late resource failures; `LIMIT 0` side effects; and indeterminate-commit reopen. `List1[5]` remains excluded for unsupported `toInteger`; `Remove1[2,4]` remain excluded for `keys`; `Remove1[7]` remains excluded for `keys`/`sum`; rejected-profile rows are not passes. The coordinator alone owns generations, WAL, publication, and outcomes ([writes.md:9-31](../../../docs/graph/plans/writes.md#L9-L31), [writes.md:49-61](../../../docs/graph/plans/writes.md#L49-L61)).

The existing staging component is useful evidence that those future operations have a real target interface, but it is not execution evidence. The repository's scheduling contract makes the distinction explicit: controlled components cannot prove native admission, durable commit, recovery, close-drain, or original TCK execution, and plan construction never increments TCK counts ([parallel-contracts.md:18-24](../../../docs/graph/plans/parallel-contracts.md#L18-L24), [parallel-contracts.md:48-56](../../../docs/graph/plans/parallel-contracts.md#L48-L56)).
